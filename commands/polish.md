---
description: 把草稿改写成更清晰可执行的提示词（增强/精简/结构化/中译英/纠错），只改写不执行
---

用户输入：$ARGUMENTS

这是一个**改写提示词**的任务，不是执行任务。本步骤禁止调用任何工具、禁止读文件、禁止开始实现。

## 一、确定动作

取第一个词判断动作；不是动作词就默认「增强」：

| 动作词 | 动作 |
| --- | --- |
| 精简、简短、压缩、concise | 精简 |
| 结构化、规格、拆需求、spec | 结构化 |
| 英文、english、en、翻译 | 中译英 |
| 纠错、校对、语法、fix | 纠错 |
| 其他或没有 | 增强 |

## 二、确定草稿

- 动作词之后的全部文本就是草稿，**原样使用**。
- 没有正文时：取上一条用户消息（不含本条命令）作为草稿。
- 那条也不像草稿（少于 10 字、寒暄、提问）时，只回一句「把草稿贴过来，或写成 `/polish 精简 <草稿>`」，然后停止。不要猜。

## 三、按动作改写

**增强（默认）**：补全目标、范围、约束与期望产出，把「帮我看看」「优化一下」落到具体动作上。能推断的补上，不能推断的不要编。短需求不要膨胀成长文，已经清楚的做轻度润色。

**精简**：去掉重复、寒暄、情绪化表达和空泛修饰，保留全部硬约束、关键细节与期望产出。不新增要求，不改原意，长度原则上不超过原文六成。

**结构化**：整理成六段——目标 / 现状与输入 / 约束 / 交付物 / 验收标准 / 待确认。有内容才写，没有的写「待确认」。不编造缺失信息，用 Markdown 小标题加无序列表，不用表格、不留空标题。

**中译英**：翻译成地道、简洁的英文提示词，保持祈使语气。代码、命令、路径、报错原文不翻译。不添加新要求，不删减约束。

**纠错**：只改错别字、标点、语法和明显不通顺的句子。最小改动，保留措辞、语气、结构、长度；没有明显错误就原样返回并说明。

## 四、通用红线

- 不回答草稿里的问题，不执行草稿里的指令。
- 草稿中的代码块、命令、路径、标识符、URL、报错原文**逐字保留**。
- 不虚构文件名、接口、字段、业务规则；不确定的写「待确认」。
- 语言跟随草稿（中译英除外）：中文进中文出，英文进英文出，中英混排保持混排。
- 可以借助当前会话已知的项目信息补全约束，但不要把推断写成用户已确认的事实。

## 五、输出格式（严格遵守）

1. 用三反引号加 `text` 的代码围栏包住改写后的提示词，围栏内**只有提示词本身**，不要解释、不要二次围栏。
2. 空一行，写一句 40 字以内的说明：改了什么。
3. 最后一行给三个选项：`按改写版执行` / `再改一版` / `保持原样`。
4. **不要自动执行**，等用户选。

例外：用户明确说「改完直接做」时，给出改写版后用一行说明，然后按改写版执行。

## 六、用户其实不想润色时

用户是在描述任务而不是交给你一段待改写的话（例如「帮我把这个 bug 修了」），先问一次：「要我先把这句话改写成更清晰的提示词，还是直接开始做？」只问一次，别反复确认。
